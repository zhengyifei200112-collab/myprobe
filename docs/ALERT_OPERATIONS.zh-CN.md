# 故障事件与通知投递

适用于 incident-outbox 开发分支。当前 PR 尚未完成全部验收或发布；本说明不表示主分支已经具备这些新增能力。

## 查看故障

进入管理中心 → 告警 → 故障事件。列表按事件创建顺序倒序排列，可按状态和节点组合筛选；每次加载 25 条，使用“加载更多事件”查看更早记录。“刷新”重新读取当前筛选结果。

| 状态 | 含义 |
| --- | --- |
| 等待触发 | 条件异常，尚未达到触发持续时间 |
| 故障持续 | 已满足触发条件，尚未确认恢复 |
| 已恢复或结束 | 满足恢复条件，或因规则停用、修改、删除而结束 |

已结束事件会显示具体结束原因；规则管理操作与观测恢复分别标明。全部节点视图保留已删除节点的历史。

状态与通知渠道是否可用无关。通道停用、凭据无法解密或投递失败时，故障仍然记录。

数据过期时，页面显示等待新观测的提示。旧指标不能证明已经恢复；触发和恢复窗口均需要重新积累连续的有效观测。资源数据和探测结果默认以“60 秒或三个配置间隔中的较大值”判断是否过期。未来超过 30 秒的时间戳也视为未知。

旧版本导入的事件会标注时间近似，不能据此推断精确故障开始时刻。历史发送记录保留在“发送历史”中；它不是当前故障数量的统计依据。

## 知悉故障（开发分支功能）

在“故障事件”卡片中点击“查看处理记录”，也可以从“查看投递记录”进入同一事件详情。“知悉与处理记录”提供可留空的管理备注；点击“知悉此故障（继续通知）”记录当前登录操作者和服务器时间。备注规范化后最多 1000 个 UTF-8 字节，中文通常每字 3 字节。

知悉表示有人处理，不代表技术故障已经恢复，也不会暂停通知或重复提醒。首次知悉的操作者、时间和备注保留；其他人的后续知悉不会覆盖原记录。已结束事件不能新建知悉，已有记录仍可查看。事件列表仅显示操作者和时间，完整备注只在受保护的详情中展示；不会出现在公开节点数据和告警消息中。

发送结果未知时使用“重试确认知悉结果”，保持原请求。当前标签页刷新后仍可继续；即使选择了另一事件，重试也只确认原事件。浏览器存储不可用时不会开始提交；记录损坏时先核对事件知悉与审计，再清除本地记录。清除不撤销服务器操作，也不证明原请求失败。关闭标签页可能丢失记录，恢复旧数据库会回退知悉及重试历史，恢复后先核对备份时间。

页面若提示事件已被知悉，显示的是首次记录，您的新备注未另行保存。点击“刷新知悉记录”核对查询时状态。限时静默、“知悉并静默”和聚合仍为独立后续工作，不能把知悉视为静默开关。契约及验证见 [知悉开发说明](INCIDENT_ACKNOWLEDGEMENT.md)。

## 配置触发与恢复

在“告警规则”中设置触发持续时间。新规则默认勾选“恢复窗口与触发持续时间相同”；取消勾选后可单独设置恢复持续时间。0 秒表示立即触发或恢复。旧规则原来立即恢复的行为会保留。

重复提醒用于仍在发生的故障。发送失败的重试属于同一个投递任务，不是新事件；慢渠道不会阻塞其他规则的故障评估。

修改规则的节点、通道、类型、阈值或时间配置可能结束原事件，并按新配置重新评估。因管理操作结束事件不等于节点技术故障已经恢复，不会伪造恢复通知。

## 检查是否送达

在事件卡片中选择“查看投递记录”。键盘激活后，焦点移动至详情标题。

| 投递状态 | 建议操作 |
| --- | --- |
| 等待发送 | 等待工作协程或重试时间；观测陈旧时可能暂停 |
| 发送中 | 已取得投递租约，等待渠道响应 |
| 已送达 | 渠道接口确认接收；不代表收件人已阅读 |
| 发送失败 | 当前任务已遇到永久错误或耗尽五次尝试 |
| 已取消 | 事件、规则或通道状态已使该任务不再适用 |

选择“查看每次尝试”查看时间、结果和脱敏错误分类。`http_rate_limited` 表示限流；`http_client_error` 表示请求被明确拒绝；`channel_configuration` 表示通知配置无法读取或验证。修正配置后，可使用通道测试检查连通性；已终止的任务不会自动改回等待发送，持续故障按规则的重复提醒产生后续任务。

“结果未知，可能已送达”表示没有取得可靠确认，例如请求发出后超时、发送进程中断。系统仍可能重试，接收端可能看到重复消息。Webhook 携带同一任务跨尝试稳定的 `Idempotency-Key`，接收端实现去重后才能利用该标识；其他渠道不能保证严格只发送一次。

默认最多尝试五次，重试基础间隔为 30 秒、2 分钟、10 分钟、30 分钟，并加入最多 20% 的正向随机延迟。渠道给出更长的 `Retry-After` 时遵守该等待时间。明确的永久拒收不继续重试当前任务。

## 升级与运行

- 维护页的节点配置导入导出不包含告警策略。范围策略页提供独立策略文件；事件、投递历史及通知凭据的迁移仍需完整数据库备份与原加密密钥。
- 恢复备份会回到备份时的投递状态。备份后已送达的通知可能再次发送，接收端幂等去重仍有必要。
- 升级前备份数据库，并单独保存原加密密钥。更换或丢失密钥会导致原通知配置无法解密。
- 未发布的迁移 015 将旧活动状态转换为事件。旧的成功发送不会直接重新入队；失败任务保留原有效等待时间，并从下一次尝试接续。
- 启动后先完成一次事件评估，再启动投递工作协程，避免旧任务先于当前观测发送。
- 当前不自动删除新增事件和投递历史。管理员应关注数据库增长；备份恢复仍遵循现有部署文档。
- Schema 升级是向前迁移，不能假设换回旧二进制就能回滚。需要回滚时使用升级前备份，并评估备份之后的数据损失。

## 范围策略与配置转移（开发分支功能）

在“告警 → 范围策略”中按全部节点、标签或指定节点创建策略。同一策略键依次按指定节点、标签、全局选择，再比较同层级优先级；不同策略键独立生效。逐节点继承预览解释当前选择，但不证明通知已送达。

旧单节点规则会在评估前映射到范围策略，保持执行规则身份。规则卡片显示归属，使用“编辑所属策略”修改；一次策略修改可能影响多个节点。配置通常在下一次 15 秒评估时应用。页面显示最近成功应用时间；失败状态不能当作新配置已生效。

转移步骤：

1. 在来源环境展开“策略导入与导出”，下载策略文件。文件仅包含策略定义及引用 ID，不包含渠道凭据、模板正文、事件或历史投递。
2. 在目的地先创建通知渠道、需要的模板及节点，再上传策略文件。当前接受 v1 格式、每批 1—1000 条策略；请求上限 16 MiB，目标环境策略总量也受 1000 条限制。
3. 为每个源渠道、显式节点和模板选择目的地对象；即使 ID 相同也需要明确映射。不会按名称匹配或覆盖已有策略。标签按目的地节点动态匹配，未来节点和标签变更会改变范围。
4. 点击“预览导入”，展开各策略检查归一化配置。修改映射会使旧预览失效；提交时重新检查引用和启用策略冲突，整批成功或整批不写入。
5. 点击“确认新增策略”。成功只表示配置已保存，继续查看评估状态和实际事件；不会复制来源环境的活动故障。

### 导入失败或结果未知

输入或策略冲突被明确拒绝时，调整文件或映射并重新预览。模板在预览后被删除，也会拒绝整批提交。目的地渠道凭据、模板内容和标签成员不会被预览锁定。

网络中断或服务端错误可能发生在提交成功之后。页面保留原请求，使用“重试确认导入结果”；不要重新建立一批导入。当前标签页刷新后仍能恢复原请求。相同请求返回当时创建的 ID，即使对象后来被删除也不会重新创建；返回历史结果不保证对象现在仍存在。

恢复记录存放在当前标签页的浏览器存储，关闭标签页可能丢失。浏览器存储不可用时不会开始提交。损坏的恢复记录会暂停新的导入；先核对策略列表和审计记录，再使用页面提供的清除按钮。清除本地记录不撤销服务端变更，也不证明先前请求失败。

数据库恢复也会回退导入重试历史。备份中已包含的请求仍返回原结果；备份后才提交的请求不在恢复后的记录中，再次提交可能创建新的策略 ID。恢复数据库后，先核对备份时间和当前策略，再处理浏览器里保留的待确认请求；不能把跨越恢复时间点的重试当成必然无副作用。

策略导入重试历史当前最多保留 10000 条且不会自动清理。达到上限时拒绝新导入，已记录请求仍可确认；不要手工删除历史来重试不确定的请求。完整迁移、跨版本升级和恢复前应在隔离环境演练。

维护窗口与事件知悉已有开发分支管理页面与 API，并通过真实浏览器及本地通知接收端验证。静默和聚合通知继续作为独立 M2 工作。范围策略的实现证据与剩余发布门槛见 [范围策略开发说明](ALERT_POLICIES.md)，事件投递说明见 [开发说明](INCIDENT_DELIVERY.md)。

## 维护窗口（开发分支功能）

在“告警 → 维护窗口”选择指定节点或标签，填写时间和原因，点击“预览维护窗口”。时间按当前浏览器时区输入；核对预览中的时间、时区、原因和成员，再确认创建。修改表单后需要重新预览，成员变化也会在提交时拒绝旧确认。刷新维护列表会更新节点候选项。

列表显示即将开始、进行中、已结束和已取消。展开记录可查看冻结成员、原选择来源及操作人；窗口可提前或在运行时取消，保留历史。多个窗口重叠时，取消其中一个不会解除其他窗口。投递记录中因维护取消的通知提供说明和维护入口。

事件投递详情会分别显示节点在查询时的维护状态、事件处理时记录的关联窗口。因维护取消的通知可以展开“此通知关联的维护窗口”，查看原因、起止时间及关联记录时间。窗口时间按原窗口时区展示，记录时间按浏览器时区展示；查询状态是快照，可点击刷新核对最新情况。

“维护期间评估事件”“观测间隔涉及维护”“队列通知抑制”代表不同处理依据；队列抑制包括领取、发送前检查，以及创建静默时取消真实待发送任务的组合判断。记录时间不能当作故障实际开始、恢复或外部收件时间。当前范围生效也不代表过去一定有通知被取消；旧历史没有自动补录，空关联不能证明从未发生过抑制。维护结束后的新通知不会继承旧通知的窗口关联。

提交结果未知时，页面锁定新的操作并提供“重试确认维护结果”。原请求在当前标签页刷新后保留。浏览器存储不可用时不会发送请求；记录损坏时先核对窗口和审计，再明确清除本地记录。关闭标签页可能丢失待确认记录；清除记录不撤销已保存窗口，也不证明先前操作失败。

先调用完整预览，核对时间、时区、原因和成员，再用返回的规范化内容、确认摘要及唯一请求 ID 创建。指定节点或标签 all/any 均可使用；创建后成员冻结，新匹配节点不会自动加入。每个窗口最多 100 个成员，当前最多保留 1000 个窗口；这属于实现限制，尚无完整容量承诺。

维护期间继续采集和记事件，抑制通知。窗口结束或取消后，持续故障须有新鲜观测才恢复提醒；维护内已恢复的故障不补发。多个窗口重叠时，最后一个有效抑制结束后才恢复通知。已发往外部渠道的请求可能无法撤回。

“已取消”表示这个投递任务不再重试，并不能证明外部渠道没有收到消息。维护生效时若请求已经发出，稍后取得的成功、拒收或不确定结果仍记录在“查看每次尝试”中；成功确认会显示单独说明。任务继续保持取消，取消时间与尝试完成时间分别保留。发送进程退出后未取得的回执仍为结果未知，不会凭取消状态推断失败。维护结束后需要的新摘要属于新的投递任务。

创建响应丢失时保持原请求内容和请求 ID 重试，返回当时创建的窗口 ID。取消使用原版本号，同一操作者重试会返回原取消时间。客户端不能指定操作者。已结束窗口不能新建或取消，历史成功请求仍可确认。删除节点不会删除窗口的历史成员。

恢复数据库会回退维护及重试历史；备份后的操作可能在重试时重新执行。恢复后先核对窗口与审计。接口、错误码、剩余发布门槛见 [维护开发说明](ALERT_MAINTENANCE.md)。

## 限时静默与知悉并静默（SIL-01/SIL-02，未发布）

在“告警 → 故障事件”打开事件处理记录，使用“限时静默”。填写 1 分钟至 7 天的时长及可选原因，选择“仅设置静默”或“知悉并静默”。期限按服务端时间计算，页面用浏览器时区显示准确截止时间、操作者及核对时间；到期后刷新确认当前状态。同一事件已有生效静默时不能叠加，请取消或等待结束。

静默只影响这个持续故障事件的通知，采集和故障评估继续。静默内恢复会结束事件和静默，不补发这期间的恢复消息；下次故障使用新事件，不继承旧静默。“知悉并静默”只在尚未知悉时将原因写入首次备注，已有原操作者、时间和备注不会覆盖；单独知悉仍不暂停通知。

取消按钮使用当前修订号。静默与维护按“任一生效就抑制”组合：取消静默后，维护仍可能生效；全部结束后等待新鲜观测，持续故障生成当前摘要并恢复正常重复间隔。陈旧数据不会强行通知。旧待发送任务始终保持取消，已发出的请求无法撤回；迟到回执继续记录实际结果。

展开静默历史查看原因、设置/取消操作者、恢复或管理结束原因及实际评估记录。投递记录分别显示维护和静默的准确关联；后来新增的静默不会改变旧通知的取消原因。原因及操作者仅管理端可见，不进入公开节点、Agent 数据、通知正文或审计正文。

创建或取消结果未知时，页面保存原操作到当前标签页，使用“重试确认静默结果”。刷新或选中其他事件后，仍重试原事件、原内容、原期限及修订号，不建立新请求。请求身份冲突、登录失效或服务端错误时保留记录，先核对历史与审计。损坏或无法写入的浏览器存储会阻止新操作；核对后手动清除本地记录不会撤销已生效静默，也不能证明原请求失败。关闭标签页可能丢失本地恢复记录。

完整数据库备份包含静默、实际决策、投递关联和原请求结果。恢复会回退备份之后的动作；恢复后先核对备份时间及事件历史再重试。配置导出不替代完整数据库备份。当前不自动清理事件和静默历史，数据库容量验证与整条发布链仍待完成。详细契约见 [INCIDENT_SILENCE.md](INCIDENT_SILENCE.md)。
