## 当前证据与问题

接入前 `internal/scheduler/scheduler.go` 只在内存保存下次派发时间，节点离线时每轮重试，
重启后重新开始；`Gateway.pending` 也承担内存任务匹配。旧 `latency_samples` 保存结果而不保存
任务 ID，旧汇总只有计数和延迟总和。因此已有成功率不能用于推算计划次数、缺测、
真实 ICMP 丢包、P95 或跨桶抖动。

当前 `ListTargetAssignments` 按启用目标和直接分配关系调度，不按节点 `latency_mode`
过滤。该字段是现有显示选择，新增统计不得借机改变已有任务分配语义。
目标组最终也写入 `node_targets`，计划生命周期必须覆盖直接分配、目标组和导入路径。

## 计划与生命周期

1. 为节点/目标保存持久计划 epoch，冻结 kind、host、port、interval、timeout、开始/结束时间。
   同一节点/目标最多一个活动 epoch。只有实际执行定义改变、启停或分配改变才开关 epoch；
   改名称、顺序、公开/隐藏和展示选择不重新排期。
2. 新增前向迁移 042，在同一配置写事务内维护 epoch，覆盖 `node_targets` 及目标定义变更。
   初次迁移只从当前配置建立已知边界，不回填旧计划。配置开始在下一整数秒生效，
   时间区间统一为 UTC 的 `[start,end)`；同秒多次修改允许空 epoch，但不得重叠或重复计数。
   时钟后退时新边界不早于本对计划已保存的边界。
3. 每个 epoch 使用固定 anchor 和 interval 推导计划槽，重启保持原 phase。
   Server 停机期间的计划由区间算术获得，不重放积压探测，也不创建无界缺测行。
   只派发当前仍处于有效派发窗口的槽，过期槽在统计中表现为缺测。
4. 实际尝试使用持久任务行，唯一键 `(epoch_id,scheduled_at)`，任务 ID 全局唯一。
   创建任务后才能向 Agent 发送；派发状态、离线、执行忙、发送失败与收到结果分别保留。
   领取使用有期限的租约；故障恢复不凭内存计数重建计划或重复创建同一槽。
5. 按任务绑定的节点、目标、kind、epoch 和期限验证结果。结果状态与原始延迟样本在同一
   事务提交，成功提交后才 ACK；同任务相同结果重放不重复落样本，冲突结果明确拒绝。
   存储失败不能先消耗唯一有效任务。迟到、过期、配置已替换、删除和重启均有专门测试。
6. 原 v1 Task/LatencyResult 字段已经有任务 ID，基础台账不要求旧 Agent 升级。
   已发布 Agent 实测兼容仍是门槛。地址族、已发/已收包数等新证据采用显式 v2 能力，
   不能给 v1 添未协商字段，也不能把旧记录默认补成 IPv4 或“一包已发”。

计划 epoch 的内部目标地址只用于有权限的执行与诊断。公开查询仅返回允许公开的节点和
目标别名，任务 ID、地址、端口、详细错误和管理备注均不直接公开。

## 统计口径

时间范围使用 `[start,end)`。只把已经过结果接收期限的计划槽放入最终统计分母，
未成熟槽数量单列；界面同时解释请求范围、统计截止和已知计划起点。

| 字段/指标 | 定义 |
| --- | --- |
| 计划数 | 已知 epoch 内已经成熟的槽数，包含 Server 停机期间 |
| 执行成功/失败 | 有可信结果且实际进入探测的成功/失败数；DNS 等失败分类保留 |
| 回报未执行 | Agent 回报 busy、unsupported、invalid_task；是缺测的子集 |
| 派发缺测 | 有任务但没有可信执行结果，区分 offline、write_error、dispatch_unknown、missing；是缺测的另一子集 |
| 缺测 | 已成熟但没有可信执行结果的槽；不得算成探测失败或成功 |
| 覆盖率 | `(执行成功+执行失败)/成熟计划数`，零分母为 null |
| 失败率 | `执行失败/(执行成功+执行失败)`，零分母为 null |
| P50/P95 | 成功 RTT 的 nearest-rank 分位数，返回成功样本数及精度/来源 |
| 抖动 | 同一 epoch、同目标、计划相邻且均成功的 RTT 绝对差之和/配对数；否则断开序列 |
| ICMP 丢包 | 仅有可信 sent/received 证据时计算；工具缺失、DNS 失败和缺测不进入包分母 |

未执行原因是缺测的可解释子分类，不能再次相加到总缺测数，必须满足
`成熟计划数 = 执行成功 + 执行失败 + 缺测`。收到但过期/冲突的结果另作管理诊断，
不能扩大分母。旧历史没有 epoch 时计划数/覆盖率不可用，绝不从当前 interval 反推。

## 分布、抖动与保留

原始范围可用全部成功样本计算精确分位数。跨桶采用可合并的 `histogram_v1`：
先按微秒向上量化，保留八个有效二进制位，以非空 bin 的下界和计数稀疏编码；
零单独编码，最大 RTT 仍为协议规定的 60000 ms。返回 quantile 的上下界和版本。
设计误差预算为 1 微秒量化加不超过 1% 的相对区间宽度，必须用边界及分布测试证明；
合并只加计数，禁止平均各桶 P95。编码版本、计数溢出、非法 bin、非有限 RTT 和损坏数据
均需拒绝；编码必须限制 bin 数和字节数，不能让输入分布造成无界分配。

汇总同时保存成功 RTT count/sum/min/max、计划/执行分类计数、抖动差值和/配对数，
以及首尾槽、首尾成功状态和 RTT。只有相同 epoch 的相邻槽才补跨桶抖动配对。
不同 epoch、失败、未执行、缺测都断开序列。

旧 rollup 没有分布或序列边界，不伪造回填；混合旧数据时明确返回不支持的字段及原因，
不能仅取新部分样本却把结果标为完整一年。新台账和汇总与现有通用历史接口分开演进。
采用既有 7/30/365 天的层级边界，清理分批提交；原始转汇总与原始删除同事务、保持幂等。
关闭 epoch 仅在全部相关记录过保留期后清理。完整备份/恢复必须保留已知计划起点和边界。
显式删除节点或目标沿用现有级联删除其历史的语义；保留期规则适用于仍保留的对象。

### 持久派发与结果确认

- 调度只派发当前槽的前五秒，不重放停机期间积压；全局使用四个有界工作线程。
  错过窗口或另一工作线程已领取属于 `skipped`，不归为目标探测失败。
- 每槽唯一任务；确认没有会话时按一秒退避，仍在有效窗口内才重试且保持原任务 ID。
  写失败可能已经送达；此类任务记为 `sent_unknown`，不再自动发送第二次。
  过期发送租约每轮最多处理 1000 条，使用专用索引转为未知；原结果仍可在接收期限内提交。
- 直接内部诊断任务同样持久化和确认，但标记 manual，没有计划槽，不进入覆盖率分母。
  `pending_results` 继续表示当前进程的传输观察，不充当持久授权或队列总数。
- 结果校验节点、目标、kind、任务接收期限及计划仍有效；配置替换后不能写进新计划。
  结果 hash、状态和旧历史样本在一个事务内保存，失败没有成功 ACK，之后可重试原结果。
  同内容重放返回匹配新封套 sequence 的 ACK，只存一条样本且不重复发布节点更新；冲突拒绝。
- canonical hash 将完成时间归一为 UTC；非有限 RTT 被拒绝。unsupported/busy/invalid_task
  属于 not_executed，成功/失败探测与未执行分别保存。
- v1/v2 原任务消息不变。台账可识别重试，不表示已发布或当前 Agent 已自动重发丢失结果；
  旧 Agent 的缺测按实际证据报告，可靠结果重发能力另行协商和验收。

043 另外保存 `known_results_since`，与 042 的计划已知起点分开。统计必须取两者较晚的
边界并解释升级过渡窗口；已有计划不代表旧结果已经有任务身份。升级不重置既有 phase，
不把 042—043 之间无法关联的旧样本直接算成缺测，完整恢复保留这两个原始边界。

### 内部统计与有界归档（迁移 044）

`internal/networkquality` 提供有界稀疏直方图与 epoch 序列段。原始成功样本使用精确
nearest-rank P50/P95；查询触及任意汇总段时，合并所有成功样本的直方图计数，返回
`histogram_v1`、区间中点以及 P50/P95 上下界。所有可表示 bin 的区间宽度均满足
`1 微秒 + 1% × 下界`，测试还以随机/边界样本核对真实分位数是否落入区间。
平均 RTT 与抖动保留原浮点总和，后者仅在同一 epoch 的计划相邻成功槽之间配对。

`PublicNetworkQuality` / `AdminNetworkQuality` 是 Store 方法，并非 HTTP 接口；公共方法
在读取时拒绝隐藏节点。现有范围汇总路由在同一读快照内校验整个批次的公开/分享/管理
范围，再投影显式 DTO；详见 [API 契约](NETWORK_QUALITY_API.md)。
查询使用一个 SQLite 读事务，区间为 `[start,end)`，未过 timeout+15 秒接收期的槽单列
pending。成熟计划数由不可变 epoch 算术计算，Server 停机不会生成无界缺测行。
没有分母或成功样本时相应指标为 null；旧计划/可信结果起点以前不推算统计。

迁移 044 新增独立 rollup 和历史边界表，不改旧延迟图表或协议。每批至多归档
32 个原始分钟桶和 32 个一分钟到五分钟桶；每种过期删除至多 1000 行。
固定相位和最短 5 秒间隔保证一个原始分钟桶至多 12 条任务。原始读取、校验、保存
汇总和删除原始任务属于同一写事务；分钟合并须等待该五分钟范围全部原始任务完成归档，
避免后续写入覆盖已有汇总。不保存全缺测桶，计划区间仍能精确解释这些缺测。
损坏记录、汇总重叠或归档冲突中止整个事务，不降级成部分健康数据。

沿用配置中的 raw/one-minute/five-minute 保留时长，默认 7/30/365 天；归档只处理
至少已经过最长 75 秒接收窗口的完整分钟。已公布的三个边界只能前移，时钟回退或
延长保留配置不会复原已删除细节。未过最长接收期的任务不会被极短配置提前移除。
手动诊断任务独立过期，不进入计划、覆盖率或分位数。关闭 epoch 在保留期外且没有
任何相关原始任务/汇总后才删除；活动 epoch 保留。显式删除节点/目标仍沿用历史级联。

查询起点位于分钟层或五分钟层时，整个请求分别使用 60 或 300 秒边界，向内对齐并返回
实际起止时间和 `partial_resolution`；不擅自扩大请求，也不按比例拆分直方图。
请求早于可用起点显示历史受限；范围完全不可用返回 null 指标。一个查询最多处理
4096 个 epoch、350000 条任务/汇总，超限明确不可用，不返回截断分布。任意历史 AsOf
若切入已经归档的不可拆分桶，也明确拒绝；未来 HTTP 路由由 Server 固定实际 AsOf。
这些是内部安全工作量上限，不能当成已测得的交互延迟承诺。

main 启动独立归档循环，100 ms 后首次运行；有积压每批间隔 100 ms，无积压等待
配置的保留间隔，错误退避 5 秒，取消时退出。管理健康接口提供
`retention.network_catchup_job` 和 `network_worker`，诊断导出只包含有界 job/worker 状态，
不含目标地址、原始结果或汇总内容。任务成功表示一批提交成功，不证明积压已清空。
