# 主机、延迟与流量历史汇总：性能与时间正确性

此实现属于 `feature/history-retention-capacity`，基于 Agent 运行证据 #63 的文档 head `64c5f26100f3d52df18449098d08e9c213ef43f9`。当前为开发与验收工作，不代表完整 PERF-01、M4/M5、24 小时稳定性或正式发布已经完成。

## 实测发现及实现

旧汇总有两个查询成本问题。六类原始/分钟汇总的去重查询只定位节点/目标/层级，逐个解析已存桶时间，不能定位具体桶；原始源及删除锚点查询则扫描全部保留数据。实测 5 节点的连续一年数据约 827 MiB：一小时追赶在 30 秒上下文内未完成，报告写入出现 5 次数据库等待超时；取消后数据事务完整回滚。

新增迁移 041 为主机、延迟与流量建立精确 epoch 桶索引；全局保留索引先选择到期区间，再执行分组与删除。原始查询显式使用范围索引，避免 SQLite 为减少排序而扫描整个节点时间索引；已有节点索引保留。查询计划回归直接使用生产 SQL，要求每个桶通过所有身份维度与时间定位，且源由到期范围读取。

性能排查同时复现了既有时间错误：可变长度 RFC3339Nano 的字符串顺序不等于时间顺序。整秒的 `...00Z`、`...00.1Z` 与 `...00.11Z` 会错序；起始/保留边界也可能丢失同一秒内的样本。SQLite 日期函数还会把 `...59.999999999Z` 四舍五入到下一秒，影响桶归属。

041 为两个原始样本表添加虚拟 `captured_sort_ns`，把应用保存的 UTC 小数秒补齐九位，保留原始 `captured_at` 和 JSON 字节。索引和范围参数使用相同排序格式。原始汇总、计数器锚点、历史查询与最新延迟按正确时间排序；原始桶先取 UTC 整秒再计算，不让日期函数的毫秒舍入改变真实桶。汇总层仍使用原 epoch 身份，兼容原有零小数或时区等价的桶格式。

未新增公开 DTO、Agent 消息、入站端口或远程命令。数值或桶发生变化的情况是上述时间错误的修正；历史的日期、字段类型和权限边界保持。

## 事务与恢复约束

六类汇总、原始删除、计数器锚点、分钟/五分钟保留及原 HTTP 批次仍在同一事务中完成。任一阶段失败或取消都回滚；不把未完成的部分桶交给历史查询。重复执行保持原桶去重，真实计数器重置继续按已有规则记账。

索引优化没有把任意积压拆成有界事务。这里测量的是正常前一轮结束后一小时的追赶；更长中断、极端重复样本、低配机器仍可能造成较长写锁。须在后续故障注入和容量验证中测量，不能从一个正常追赶样本推断所有积压都低延迟。

升级前保留完整 SQLite 备份和应用密钥。041 是前向迁移，DDL/索引/版本记录原子提交；失败后没有半套索引或虚拟列，原始记录仍在。已有大库的索引构建会增加启动耗时、临时 I/O 和磁盘空间；不要把空库启动时间当作旧库升级预算。需要降级时恢复升级前完整备份及匹配版本，不能只删迁移记录。

测试使用升级前真实表结构，验证失败回滚、索引集合、等价桶时间、计数器重置、SQLite 一致快照及正常 Store 重新打开。纳秒用例覆盖 cutoff −1 ns/恰好 cutoff/+1 ns、0/100/110 ms 的排序、起始秒范围、最新延迟、原始数据/JSON 不变和跨时区输入保存为 UTC。

## 可重复数据与证据范围

`TestHistoryRetentionDenseCapacity` 是显式启用的磁盘 SQLite 测量，不运行公网请求、真实 Agent、整个 Server、浏览器或 24 小时墙钟。

每个节点生成连续且有实际行密度的数据：

| 数据层 | 每节点数据 | 含义 |
| --- | --- | --- |
| 原始主机 | 7 天 + 1 小时，15 秒间隔，另有前界锚点 | 正常前次清理后的一小时到期追赶 |
| 原始延迟 | 同一时段，3 目标，每目标 60 秒 | 每节点 3 个可独立统计目标 |
| 分钟汇总 | 23 天，每分钟连续一行/节点或目标 | 与 7 天原始层合计 30 天细粒度保留 |
| 五分钟汇总 | 335 天，每五分钟连续一行/节点或目标 | 与前 30 天共同覆盖一年 |

主机与流量各有一份汇总；延迟按三个目标生成。完整合成报告的时间、计数与标量列一致；不使用 `{}` 代替报告负载。最终数据使用与正常应用相同的 32 字符节点/目标 ID 长度。

数据生成、初次报告回填和索引构建不计入汇总时间，单独记录构建耗时、原库和索引后大小。检查点截断生成/构建 WAL 后开始测量，`wal_after_bytes` 仅表示测量结束时已分配 WAL 大小，**不是峰值**。并发写入使用真实 `Store.SaveReport`，20 ms 计划间隔、单个串行写线程，循环节点；长阻塞会降低实际请求数。因此记录尝试/成功/失败及最大等待，不能冒充 100 个网络 Agent 的并发吞吐。

生成前检查测试临时卷至少有每节点 500 MiB 加 8 GiB 余量。所有数据库在测试拥有的临时目录，清理不涉及项目/生产数据库。规模仅允许 5/50/100；默认跳过此大容量套件。

```powershell
$env:CGO_ENABLED='0'
$env:MYPROBE_TEST_HISTORY_CAPACITY='1'
$env:MYPROBE_TEST_HISTORY_NODES='5' # 然后按 50、100 递进
$env:MYPROBE_TEST_HISTORY_VARIANT='full'
$env:MYPROBE_TEST_HISTORY_OUTPUT='<absolute evidence JSON path>'
go test ./internal/store -run '^TestHistoryRetentionDenseCapacity$' -timeout 35m -count=1 -v
```

`baseline` 与 `lookup` 是对照模式：测试临时库移除新索引并在同一事务实现中使用旧字段/索引选择；lookup 仅重建三个桶定位索引。它们允许记录失败或取消，测试通过仅表示成功记录测量及回滚，不表示容量达标。默认 full 只要汇总或并发写入失败就令用例失败。
