# 永久服务告警导入回放：存储与读取验收

开发分支 `feature/service-replay-capacity` 基于历史汇总 #64 的 `a32fdaeda06e66776d07608da908486c64a06eb8`。本模块验证迁移 037 的永久服务导入账本，不把它当作全部永久身份账本、真实 Server 容量或正式发布。

## 行为与并发

旧 `ApplyServiceAlertImport` 在查询已提交记录前先取得管理写锁。文件 SQLite 的实际回归中，其他管理事务持有写锁时，正确旧请求等待约 5 秒并以 context deadline exceeded 返回，尽管其结果早已持久化。

新实现先验证原请求 ID、包/映射/预览和完整内容 digest，再按主键读取已经提交的回放记录。匹配记录只解码原结果并设置 `replayed=true`，不写入、不更新创建时间、不检查已变化/删除的目标，也不等待无关管理写锁。相同键异内容仍返回冲突；无记录才进入原管理写事务，并**再次查询同键**，保证两次提交之间即使出现并发 commit 也只应用一次。

新请求的上限、预览修订、目标/渠道验证、整批写入与结果记录仍在同一事务内；旧成功回放不会绕过 HTTP 管理员会话、CSRF、严格 JSON、2 MiB 限制或 no-store。API 回放继续 200，新应用 201，重复回放不重复原应用审计。

没有新迁移、公开字段或 Agent 协议。没有压缩/截断结果、删除账本、缩短保留期或放宽 10000 条上限；错误/结果语义沿用原接口。应用代码不更新已提交账本，完整数据库恢复仍保留原身份。

## 数据与验证方法

每种案例先通过真实预览/应用路径提交 1000 项服务设置，取得正常结果 JSON 和 digest。然后 SQL 复制该真实结果记录，逐级生成 1000/10000 条账本；不是执行了 10000 次真实导入，也不作为导入提交吞吐证据。

目标 ID 分别取正常应用的 32 字符与配置导入允许的最大 128 字符；请求 ID 使用合法最大 128 字符。每条结果包含完整 1000 个目标 ID、created/updated 和原 replay 标志。全部服务停用、目标为 example.test、凭据为合成材料，不运行公网任务。

每个规模分散选取 200 条记录，真正执行 `ApplyServiceAlertImport` 的验证、digest 计算、数据库读取与完整结果解码，逐次核对 1000 个 ID 与原创建/更新数量。分位数是这 200 次 Store 调用的最近秩统计，不是 API/网络或全系统 p95。

达到 10000 后，实际拒绝新身份并验证设置/账本哈希未变。删除全部服务与渠道、将正常保留运行推进 400 天后，真实原请求仍能回放；账本全量 SHA-256 覆盖 ID、digest、原结果 JSON 和创建时间。正常一致 SQLite 备份、文件完整性检查、Store.Open 恢复后验证全部 10000 条原记录哈希，并重新调用真实回放路径。

生成前要求临时卷至少 8 GiB 空间；测试目录由测试创建/关闭/清理，生产文件不参与。默认跳过大容量套件，显式启用：

```powershell
$env:CGO_ENABLED='0'
$env:MYPROBE_TEST_SERVICE_REPLAY_CAPACITY='1'
$env:MYPROBE_TEST_SERVICE_REPLAY_OUTPUT='<existing absolute evidence directory>'
go test ./internal/store -run '^TestServiceAlertPermanentReplayCapacity$' -timeout 15m -count=1 -v
```

Linux CI 同样运行完整 32/128 字符案例与恢复，不能用若干空 `{}` 结果代表满库。普通回归覆盖管理写锁期间已提交回放、写触发器拒绝但只读回放成功、原字段/时间不刷新、并发同键一次应用、过期预览/同键异内容、管理员/CSRF拒绝及原容量上限。

## 本地实际结果（2026-10-15）

Windows 10 19045、Go 1.26.5、i5-13490F（16 逻辑 CPU）、可见内存 34138931200 B、KIOXIA NVMe SSD。两个案例均完成，临时数据库与恢复副本已关闭/清理。

| 目标 ID 字符数 | 记录 | 单条结果 B | 结果总 B | 数据库 B | 200 次回放 p95 ms |
| --- | --- | --- | --- | --- | --- |
| 32 | 1000 | 35061 | 35061000 | 38576128 | 2.00 |
| 32 | 10000 | 35061 | 350610000 | 371851264 | 2.00 |
| 128 | 1000 | 131061 | 131061000 | 133931008 | 2.59 |
| 128 | 10000 | 131061 | 1310610000 | 1319620608 | 3.00 |

全库约 354.6 MiB/1.23 GiB，不能按“只有请求 ID 与摘要”估计几十 MiB。最大合法 ID 的结果文本每记录约 128 KiB，10000 条逻辑结果已约 1.22 GiB，索引/页与其他配置另计。

删除目标后的完整快照分别 371007488/1318133760 B，生成约 0.95/2.92 秒；两者恢复全部 10000 条且 ledger digest 一致。结构化原记录、机器/范围与运行源 SHA-256 见 [service-replay-capacity-2026-10-15.json](evidence/service-replay-capacity-2026-10-15.json)。JSON 字节、SQLite 分配文件及使用页数分别记录；种子 WAL 是该批结束时的分配大小，**不是峰值**。

回放不重写或删除记录；满库时先确认原请求是否已提交，之后才能决定容量治理。不得通过清除旧账本“修复容量”并让丢失响应的请求重新覆盖当前设置。
