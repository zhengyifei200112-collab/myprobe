## 1. 目标与使用方式

把 MyProbe 从能够展示服务器状态的探针，推进为能够发现异常、帮助定位问题、低成本管理多节点的日常监控工具。

优先服务用户自用、最多约50台VPS的实际场景。先改善每天使用的核心流程，再完成现有服务监控和网络分析；100/500节点不属于本次交付容量目标。

本文件用于拆分开发任务和制定验收标准。现有事实以代码为依据；接口、表名、默认值和工作量均为建议，须在对应任务开始时复核。本文不替代现行 PRODUCT_SPEC.md 和 PROTOCOL.md，不应把规划功能提前标记为 Implemented。

### 1.1 用户成功标准

| 场景 | 希望达到的结果 | 验证方法 |
| --- | --- | --- |
| 每天打开首页 | 在 5 秒内找到需要处理的节点 | 使用包含离线、过期、资源异常的测试数据做任务观察 |
| 新增一台机器 | 安装后自动加入既定监控策略 | 添加匹配标签的节点，确认策略生效且不重复告警 |
| 收到报警 | 直接进入对应节点、故障和时间范围 | 从通知链接完成一次排障路径 |
| 计划维护 | 正常记录异常，但不产生预期内的通知轰炸 | 在维护窗口中断连并恢复 |
| 检查网站 | 能区分机器在线与网站服务异常 | 主机在线时模拟 HTTP 500、内容错误及证书异常 |
| 比较线路 | 知道观测方向、样本完整性和延迟分布 | 多节点监测同一目标，验证缺测不会被当成成功 |

### 1.2 保持的产品边界

- 保持单 Server、SQLite、轻量 Go Agent 和主动出站连接的部署方式。
- 保持公开展示与管理权限分离，公开数据由服务端筛选。
- 保留现有一键安装、备份、迁移、主题和共享能力。
- 本路线不引入远程 Shell、任意命令执行、自动故障修复和终端代理。
- 暂不建设日志检索、分布式链路追踪、Kubernetes 平台或大型插件市场。
- 不因功能增长直接更换数据库；先通过容量测试确定真实瓶颈。

## 4. M1：日常使用效率

### 4.1 首页搜索、过滤与排序

用户故事：我知道机器名或标签，想快速找到它；发生异常时，我只想看需要处理的机器。

需求：

1. 按节点名称和公开标签搜索，忽略大小写，搜索与标签、状态筛选取交集。
2. 状态提供全部、需要关注、上报中断、即将到期；“需要关注”可含多种原因，必须显示具体原因。
3. 支持后台顺序、名称、CPU、内存、延迟、到期时间排序。数值缺失始终排末尾，使用节点 ID 稳定打破平局。
4. 多目标延迟排序必须先选择目标，不能取某个任意目标混合比较。
5. 状态统计明确区分全部节点与当前筛选结果；清空筛选入口始终可见。
6. URL 保存可分享的查询条件；本地保存视图和排序偏好。首次进入以 URL 为优先，随后才读本地偏好。
7. 增加表格视图，默认列为名称、状态、CPU、内存、上下行、指定目标延迟、到期；手机端允许横向滚动并保留名称列。
8. 动态排序采用节流更新，并在用户操作期间避免行位置反复跳动。

状态语义：

- 浏览器与 Server 失去连接：全局提示“实时连接中断”，不能把所有机器改成离线。
- Agent 超时未上报：显示“上报中断/最后上报时间”；单凭这一条件不能确认服务器断电。
- 资源数据陈旧：旧值降低视觉权重，显示更新时间，不伪装成实时值。
- 首次尚无数据：显示“等待接入”，不归入资源正常。
- 公开首页的异常原因只能来自允许公开的数据；管理侧告警阈值、备注和通知信息不随之公开。

验收：100 个模拟节点可按组合条件准确筛选；空结果能恢复；刷新可还原查询；实时事件不会清空条件；360/768/1440 px、明暗主题均可操作；搜索和表格支持键盘。

### 4.2 表单单位与字段改进

| 字段 | 输入体验 | 数据约束 |
| --- | --- | --- |
| 价格 | 金额 + 币种 | 用十进制字符串转换为最小货币单位，按币种小数位处理，不用浮点乘法直接入库 |
| 周期 | 月付/季付/半年/年付/一次性/自定义 | 旧自定义值保留，不强行改成枚举 |
| 带宽阈值 | 数字 + 单位 | 明示 bit 与 byte；Mbps 为十进制，MiB/s 为二进制 |
| 流量阈值 | 数字 + GB/GiB/TB/TiB | 后端仍存字节，明确精度和范围 |
| 持续/冷却时间 | 秒/分钟/小时 | 统一转换为秒，保持现有约束 |
| 到期时间 | 本地时区提示 | 传输和存储 UTC，保存后回显时区 |
| 节点排序 | 上移/下移，拖动为增强 | 保留键盘操作及整数顺序兼容 |

验收：旧记录打开保存不改变金额和阈值；0、小数、边界值、币种切换得到确定结果；超过 JavaScript 安全整数范围的字节值使用字符串契约或明确拒绝，禁止静默取整。

### 4.3 批量管理

第一版允许批量增删标签、设置可见性、采集/上报间隔和探测目标；目标操作必须明确“添加、移除、替换”，默认使用添加。价格、到期、Token 和删除不纳入第一版批量范围。

流程：选择节点 → 选择操作 → 服务端预览逐项变更 → 确认 → 执行 → 显示结果。初版限制每批 100 个节点，超限要求拆分。

预览返回节点版本及变更摘要；执行时再次鉴权并校验版本。使用事务保证全批成功或全批不变，冲突时列出节点并要求重新预览。请求使用幂等键；审计记录操作人、节点 ID、修改字段和结果，不写入秘密。

验收：无变化节点可见；跨页选择有明确数量；预览后被他人修改的节点不能被覆盖；重复提交不重复执行；服务端拒绝不允许的字段；管理后台可见性变化立即反映到公开 API。

## 5. M2：告警与事件中心

### 5.1 分离故障事件与通知投递

当前发送历史保留。新增事件中心作为“故障是否仍在发生”的依据；投递历史作为“消息是否送达”的依据。

建议模型：

| 对象 | 核心字段 | 说明 |
| --- | --- | --- |
| alert_policies | ID、规则条件、范围、优先级、持续/恢复窗口、通道列表、版本 | 统一策略 |
| incidents | ID、策略/节点/目标、开始/确认触发/恢复时间、最后观测、状态、原因快照 | 一次持续故障 |
| incident_actions | 事件 ID、动作、用户、时间、备注 | 知悉、静默和取消操作 |
| notification_deliveries | 事件 ID、通道、通知类型、幂等键、状态、下次尝试时间 | 逻辑投递 |
| delivery_attempts | 投递 ID、尝试时间、结果、脱敏错误 | 单次发送尝试 |
| maintenance_windows | 范围、UTC 起止、时区、原因、创建人 | 维护期间抑制通知 |

以上是逻辑模型，落地前复核现有 alert_states 等表的复用方式；不要复制两套相互竞争的状态机。

故障状态为 pending → firing → resolved。acknowledged_at 与 silence_until 是独立属性，知悉不等于恢复。用唯一约束保证同一策略、节点和目标至多一个活动事件。

数据缺失不视为恢复：资源告警在缺测时保留事件并标记观测陈旧，单独由离线策略描述上报中断。恢复须满足独立恢复窗口；默认与触发窗口一致，可显式调整。

### 5.2 策略继承

- 范围支持全部节点、显式节点列表、标签选择器；标签支持明确的 all/any 语义。
- 标签范围动态生效：新节点符合条件后自动应用。界面显示当前命中数量和示例节点。
- 同一 policy_key 的候选策略按显式节点、标签、全局的顺序匹配，再按优先级决定；相同优先级冲突在保存时拒绝。
- 不同 policy_key 可并存，例如 CPU 预警与 CPU 严重告警；界面提示重叠，避免误以为覆盖。
- 提供逐节点“有效策略”预览，解释继承来源和覆盖关系。
- 旧单节点规则迁移为等价显式节点策略，保留阈值、通道和活动状态映射；切换时不能重发全部告警。

### 5.3 维护、知悉与静默

第一版只支持一次性维护窗口，重复日历放后续。区间采用 [开始, 结束)，开始包含、结束不包含。可对节点或标签生效；标签窗口默认在创建时冻结节点集合，界面写明，避免维护期间新节点意外免告警。

维护期间继续采集、判断及记事件，只抑制通知。窗口结束后：仍异常则只发送一次当前状态；期间发生并已恢复的故障仅留历史，不补发恢复。窗口开始前已通知的事件若在维护中恢复，也只记录恢复。

知悉默认不静默；“知悉并暂停 1 小时”是单独操作。到期仍异常时恢复后续提醒，不重建事件。禁用策略后将活动事件以“规则停用”原因结束，不伪造技术恢复通知。

### 5.4 投递可靠性与聚合

事件变化与待投递任务在同一事务中提交，使用持久化 outbox 和租约消费。建议初始最多尝试 5 次，按 30 秒、2 分钟、10 分钟、30 分钟退避并加入抖动；遵守 Provider 的 Retry-After，永久鉴权错误直接失败。

幂等键至少包括事件 ID、转换类型、通道 ID、重复提醒序号。外部渠道超时可能已经接收，无法承诺严格 exactly-once；支持渠道幂等能力时使用，否则按至少一次投递并显示重复风险。

先完成可靠投递，再做默认 30 秒聚合窗口。同策略、多节点同时触发时合并摘要，并附事件入口。迟到消息发送前重查事件状态，不能在恢复后发送无上下文的旧“故障中”消息。

### 5.5 验收

- 阈值附近波动不会反复创建事件；并发评估只形成一个活动事件。
- Server 在触发、投递和恢复的各阶段重启，状态可继续。
- 通道失败不改变故障状态；通道恢复后可按策略重试。
- 维护边界、时区转换、静默到期和规则停用均有确定行为。
- 新旧规则迁移前后告警判断等价，不产生迁移引发的批量通知。
- 通知深链需鉴权；事件不存在、已删除或无权限时给出明确页面。

## 6. M3：节点详情与服务监控

### 6.1 独立节点详情

建议公开路由 `/nodes/:id`，管理路由 `/admin/nodes/:id`。路由名称为规划，实施时与现有前端入口兼容。

详情包含概览、资源、网络、事件四个区域。保留首页快捷历史弹窗，但“查看完整详情”能进入固定链接。资源与网络速率分图，时间游标联动，避免不同单位挤在同一图中。

支持预设范围、自定义绝对时间、缩放及恢复默认。API 按时间范围选择汇总粒度并返回 bucket_seconds；断点不连成正常曲线。

时间线展示上线/上报中断、资源告警、恢复、维护和配置修改。开机时长下降只能标注“检测到重启迹象”，除非有更可靠证据；Agent 重连不等于主机重启。采样系统确认的故障时间应区分首次失败与达到告警门槛的时间。

公开详情继续遵守节点隐藏和脱敏规则；管理事件、用户备注、目标秘密和审计信息仅在管理视图提供。分享链接的范围限制不能因详情路由绕过。

### 6.2 HTTP/HTTPS 监控 MVP

首版包含 GET/HEAD、允许状态码集合、文本包含断言、有限 JSON 字段相等断言、总耗时、超时、HTTPS 证书有效性及到期提醒。JSON 使用受限字段路径，不引入可执行表达式。

暂不包含任意脚本、浏览器登录、复杂认证流程、主动自动修复。首版不支持带秘密的请求 Header，避免在凭据分发机制尚未设计时把管理凭据传入 Agent。

监控由选定 Agent 执行，复用已有调度与回传通道。每个观测点独立显示结果；服务摘要默认“任一必选观测点失败即降级”，缺测为未知。后续可增加法定数量策略，但不能把多点结果未经说明平均为服务可用率。

建议初始边界：间隔不低于 30 秒，超时默认 5 秒且小于间隔，最多 3 次重定向，读取响应上限 1 MiB，Agent HTTP 并发默认 4。作为起始配置，经过负载测试后调整。

失败分类：DNS、连接拒绝、连接超时、TLS 无效、证书到期、状态码不符、内容不符、响应过大、内部执行失败。保存分类、状态码、耗时和证书摘要；默认不保存响应正文和完整敏感 URL。

### 6.3 探测边界与协议兼容

- 默认仅允许 HTTP/HTTPS、公网目标和指定端口范围；拒绝环回、链路本地及云元数据地址。
- 内网监控作为显式 Agent 配置能力，通过目标网段允许列表启用，不能仅凭面板字段开放。
- 初始解析、连接地址和每次重定向均校验，防止 DNS 重绑定和重定向绕过。
- 不允许跳过 TLS 验证；证书提醒默认提前 14/7/1 天，各档去重。
- Hello 能力增加 http_probe 等标识；调度前检查 Agent 能力，旧 Agent 显示“不支持”，不记成服务失败。
- 新任务/结果若不能由旧协议安全忽略，应发布协议 v2，并保留 v1 接入；不能只增加常量就假设兼容。
- 配置分发、任务取消、超时、重复结果和乱序回报需要协议级测试。

### 6.4 可用性口径

首版统计定义为“有效检测成功率”，显示成功次数、失败次数、应执行次数和缺测次数。成功率 = 成功 / (成功 + 失败)；覆盖率 = 有效检测 / 应执行检测。分母为零返回 null，不显示 100%。

维护内计划槽位不进入服务可用性分母，但维护时长单独展示。Agent 离线、调度未执行为缺测，不算服务成功，也不直接等价于服务失败。基于状态转换估计的故障持续时间单独标注“按采样估算”，不冒充 SLA。

验收覆盖：200、500、重定向循环、慢响应、过期/无效证书、内容错误、过大响应、旧 Agent、Agent 离线、维护期间、DNS 地址变化和重复回报。测试必须使用本地可控目标，不依赖公网网站稳定性。

## 7. M4：网络质量分析

### 7.1 指标定义

| 指标 | 计算口径 | 边界 |
| --- | --- | --- |
| 探测失败率 | 已执行失败 / 已执行总数 | 与缺测分开 |
| 覆盖率 | 实际执行 / 计划执行 | 调度跳过与 Agent 不支持单列 |
| P50/P95 RTT | 成功样本的分位数 | 附样本数和统计粒度 |
| 抖动 | 同一序列相邻成功 RTT 差值绝对值的平均 | 失败或缺测打断序列，至少两次连续成功 |
| ICMP 丢包率 | 已发送但无回包 / 已发送 ICMP 包 | 工具缺失、DNS 失败不能计入 |
| TCP 连接失败率 | 失败连接 / 已执行连接 | 不命名为丢包率 |

当前单次 Ping 结果可用于检测成功率。若新增每任务多包采样，需新增 sent/received 字段、限制包数与频率，并更新协议；不能从现有 error_class 推造精确丢包。

### 7.2 汇总与存储

时间桶至少保留计划、执行、成功、失败、缺测计数，以及成功 RTT 的 count/sum/min/max。成功率汇总使用总计数相除，禁止平均多个桶的百分比。

长周期 P95 不能取各桶 P95 的均值。实施时在可合并直方图或其他可合并分位数结构中选择一种，并测量误差与存储成本；未完成前仅在原始样本覆盖范围提供精确分位数。旧历史缺乏样本分布时返回“不支持”，不伪造回填。

抖动汇总需保存差值总和、配对数和序列边界信息，才能跨桶正确合并；否则只提供当前桶结果。所有汇总操作保持幂等，并测试跨保留层查询。

### 7.3 页面功能

- 选择目标后比较最多 8 个节点，统一时间范围、单位和时区。
- 显示“观测节点 → 目标”，IPv4/IPv6 分开配置与展示。
- 目标解析地址可写入管理诊断；公开界面仅显示允许公开的目标别名。
- 提供晚高峰预设，同时显示对应时区与绝对时间，允许自定义。
- 折线配合失败区段和覆盖率；没有数据时不绘制零延迟。
- 支持配置导入形式的目标预设，不硬编码第三方长期可用性承诺。

验收：统计与人工小样本对照；多桶成功率、分位数误差、IPv6 不可用、丢包/执行失败分类、缺测及跨天时区均验证；8 节点对比可读且请求数量受控。

## 8. M5：系统健康、备份与容量

### 8.1 系统健康页面

展示 Server 版本、运行时间、数据库及 WAL 占用、保留配置、最近汇总任务结果、调度积压、Agent 连接数量、投递队列、最近备份结果。

节点诊断展示 Agent 版本、能力、最后上报、配置版本是否生效、最近脱敏错误；浏览器连接状态和 Agent 通道状态分开。只有 Agent/Server 实际提供证据时才能展示具体连接方式。

版本提醒应区分有新版本与协议不兼容。首版提供升级文档和命令，不通过面板远程执行更新。

### 8.2 定时备份

复用现有加密备份实现。第一版支持指定本地目录、每日时间、保留份数和备份失败提醒；S3 等异地存储列为后续扩展。只允许清理本系统生成且通过路径检查的旧备份。

备份采用 SQLite 一致性快照，不直接复制活跃数据库文件。产物原子落盘，记录校验结果、大小、开始与完成时间；失败产物不替换最近成功文件。首次运行和配置保存时检查目录权限及剩余空间。

无人值守备份需要独立的密钥配置与托管说明，不能把解密口令明文存进同一数据库。数据库备份、应用加密密钥及备份解密材料的恢复依赖必须在界面和文档写清。

验收必须包含隔离环境还原、错误口令、截断文件、磁盘满和进程中断。只有恢复演练通过才显示“已验证可恢复”；仅创建文件成功显示“备份完成”。

### 8.3 诊断导出

导出版本、配置结构摘要、迁移版本、计数、最近错误分类和任务状态；默认排除数据库内容、凭据、会话、真实公网 IP、目标敏感 URL 和用户备注。导出前可预览，下载需要管理权限并留审计记录。

### 8.4 容量验证

建立可重复模拟Agent工作负载，必需容量按5→50节点递进，以15秒上报、每节点3个60秒目标、5个浏览器为主要场景。按实际故障需要补充其他频率与目标数；100/500节点仅为可选扩展，避免盲目跑完整笛卡尔积。

记录测试机器 CPU/内存/磁盘、提交版本、采样设置、数据规模、预热时间、持续时间及并发方式。代表性场景至少做 24 小时稳定性观察，历史查询用生成数据覆盖 30 天和一年保留层。

建议初始门槛：在明确记录的 2 vCPU/2 GiB SSD 环境，50节点、15秒上报、每节点3个60秒目标、5个浏览器下，24 小时无崩溃或未解释的数据丢失；概览 API p95 < 500 ms、30 天历史 p95 < 2 s、进程 RSS < 700 MiB，稳态内存不持续增长。门槛保持有效；当前短测与长测状态见[验收入口](CANDIDATE_ACCEPTANCE.md)，不得从历史规划推断验收尚未开始或已经完成。

同时量化数据库日增长、WAL 峰值、写入延迟、任务延迟和通知积压。达不到目标先定位热点并调整采样、索引和查询范围，不以降低数据正确性换取漂亮数字。

### 9.2 数据迁移

按批量配置版本、事件与策略、维护与投递、HTTP 结果、网络汇总、备份任务分别新增迁移。编号以合并时最新序号为准，不提前占用固定编号，不改写已发布迁移。

每个迁移说明旧数据默认值、索引、保留策略及运行时间风险。历史故障无法可靠重建时，明确“从升级后开始记录”；旧通知作为旧投递历史保留，不伪造成完整事件。

配置导入导出升级格式版本，支持旧版本导入并提供预览。新秘密字段遵守现有排除规则。恢复流程必须识别备份 Schema 与运行版本，不允许不兼容的旧 Server 直接读写新库。

### 9.3 回滚与发布

- 优先使用新增字段/表和功能开关，分离“数据库已扩展”与“用户功能已启用”。
- 每次升级前备份，并在临时环境验证旧 Agent 与新 Server。
- 数据库迁移保持向前；不能承诺降级二进制即可回滚。必要时恢复升级前备份，明确期间数据损失窗口。
- 发布说明列出 Agent 最低能力、协议范围、Schema、配置变更和恢复步骤。
- 新服务及网络任务先少量节点试运行，检查队列、资源开销和错误，再扩大启用范围。

已合并不自动等于已发布；草稿 PR 不自动等于模块可用。本文不维护未经查询确认的实时 PR 状态。

### 14.3 单项任务模板

每个任务说明至少包含以下内容，可直接复制到 Issue 或 PR：

1. 用户问题：何时、由谁、遇到什么具体阻碍。
2. 本次范围：入口、操作、输出，以及明确暂缓的能力。
3. 行为契约：默认值、时间/单位、权限、空值、异常和并发行为。
4. 数据影响：API、Agent 协议、数据库迁移、导入导出、备份恢复。
5. 验收用例：输入与预期输出，包含正常路径和关键边界。
6. 发布条件：必要检查、用户文档、生成资源、升级与恢复说明。
7. 完成证据：提交与 PR、实际执行的测试、未验证项目及原因。

## 15. 主要风险与设计决策

| 风险 | 设计要求 | 验证方式 |
| --- | --- | --- |
| 告警迁移后大量重发 | 保留已有活动状态和已通知信息，无法重建的历史明确标识 | 带旧状态库升级，检查通知次数 |
| 通知超时导致重复 | 记录结果未知；支持渠道幂等时复用稳定键 | 模拟接收成功但响应丢失 |
| 历史窗口混入结束时间之后的数据 | 明确采用半开区间与有效查询边界；处理汇总桶跨边界的近似限制 | 原始/汇总交界、结束边界及空窗口测试 |
| 长期分位数统计失真 | 可合并统计结构，旧数据缺分布时标记不可用 | 与原始样本结果对照误差 |
| 隐藏节点或敏感目标从新页面泄露 | 列表、详情、历史、分享分别校验服务端范围 | 未登录、登录、隐藏、删除与分享过期契约测试 |
| HTTP 探测消耗 Agent 资源 | 限并发、限正文、总超时、取消任务和地址校验 | 慢连接、大响应、重定向与任务积压 |
| 多分支迁移编号或语义冲突 | 合并前重新核对序号与升级路径，已发布迁移保持不变 | 从上一正式版本完整升级并恢复演练 |
| 备份成功但无法恢复 | 文件生成和已验证可恢复分开显示 | 隔离环境恢复数据库与必要密钥 |

历史边界的建议契约为 `[start, end)`，输出同时说明请求范围、实际覆盖范围和桶宽。原始样本可精确筛选；已经聚合的部分桶不能还原任意秒级窗口。实施时选择只纳入完整桶，或经明确展示后对齐有效范围，不能默默混入范围外样本并宣称精确。

需要在对应任务设计阶段最终决定：服务多观测点的必选集合、长周期分位数结构与误差上限、备份密钥来源、统计结果保留周期。决策记录写入对应模块文档，不提前把建议字段和默认值当作不可修改的协议。

## 16. 每阶段复审方式

每阶段结束，用至少一套包含正常、异常、缺测和隐藏节点的可复用数据走完整用户流程。记录完成时间、误操作、困惑点及是否需要查文档；优先修复妨碍任务完成的问题。

复审输出保持简洁：本阶段交付了什么、证据在哪里、仍有什么限制、下阶段优先级是否需要调整。若新增需求无法对应既定用户场景，先进入候选列表。核心取舍保持一致：先让用户发现问题、理解问题并收到可信通知，再增加监控种类与展示选项。

### 16.1 跨模块用户验收场景

以下场景用于阶段交付验收，不能只用接口成功或页面可打开代替。数据、渠道和服务目标均使用隔离测试环境。

| 场景 | 操作与故障注入 | 预期用户结果 | 保留证据 |
| --- | --- | --- | --- |
| 每天检查 50 台节点 | 混合正常、离线、即将到期、缺测和隐藏节点；搜索并组合筛选 | 能快速找到指定节点；缺测不显示为健康；公开页面不出现隐藏节点 | 数据集、操作耗时、截图与权限测试 |
| 给一批节点调整采样 | 预览变更后从另一会话修改其中一个节点，再提交原预览 | 明确提示冲突，全批不部分生效；重新预览后可执行；重复请求不重复修改 | 前后配置、响应和审计记录 |
| 一次持续资源故障 | 超阈值、短暂回落、再次超阈值；模拟通知通道超时与 Server 重启 | 活动故障不重复创建；发送失败可解释；重启后继续处理；满足恢复条件后结束 | 事件、投递尝试、状态转换时间 |
| 一次计划维护 | 在维护前、中、结束边界制造异常，分别测试窗口内恢复和持续异常 | 维护中继续记录；不补发已经消失的故障；仍异常按规则通知一次 | 窗口、事件、模拟通道收件数量 |
| 网站异常但主机正常 | 保持 Agent 在线，服务依次返回 500、错误正文和过期证书，再切断 Agent | 前三者分类显示服务失败；Agent 离线显示缺测；分母与覆盖率可核对 | 原始结果、统计计数与页面展示 |
| 收到告警后排障 | 从测试通知链接进入事件，再定位节点及历史时间范围；刷新页面 | 链接可恢复上下文；图表时间与故障一致；未登录须鉴权；无权限不泄露数据 | 深链、时间边界与浏览器测试 |
| 探针迁移到新环境 | 创建加密备份，在隔离环境还原并配置必要密钥 | 节点与策略可读取，凭据可按预期使用；验证前不标注“可恢复”；说明备份时间之后的数据缺口 | 版本、备份校验、恢复步骤和结果 |

任一场景未通过时，记录具体失败与受影响任务，修复后复验该路径。容量指标另按第 8.4 节实测，不能由上述功能验收推断承载能力。

## 17. 下一轮开发工作包

本节把近期工作拆到可直接领用的粒度；它是建议顺序，不授权合并或部署。先处理已经存在的分支与未提交改动，再开始新功能。每包完成后更新任务证据，不以新增代码量衡量进度。

### 17.1 收敛已有实现与发布基线

**目标：** 明确哪些功能已在主线、哪些需要继续评审，避免并行成果相互覆盖。

1. 为第 11 节全部任务建立实施台账，填入实际提交、PR、测试提交及发布状态；没有证据的字段标为“未核实”。
2. 对照当前主线复核已有 UX、批量管理、事件投递、详情页、健康页及 HTTP 分支；优先复用已有接口和页面。
3. 检查跨分支迁移编号和模型语义，使用上一正式版本的隔离数据库走完整升级链。已发布迁移不能改写。
4. 对每个待评审分支同步产品规格、协议、部署说明、变更日志和前端生成资源；消除“尚未实现”与实际代码相矛盾的说明。

**验收：** 每项已有成果可定位到证据；升级演练无迁移冲突；待交付范围清晰。发现依赖未合并时保持明确依赖关系，不把未合并代码标为正式能力。

### 17.2 HTTP 基础能力闭环（SVC-01 / SVC-02）

**用户结果：** 创建一项服务检查后，能够知道任务是否真正执行，以及异常来自目标服务、Agent 还是本地策略。

| 子任务 | 实施要求 | 验收条件 |
| --- | --- | --- |
| 启用与停用 | 服务端默认关闭；明确配置错误、重启生效及 Agent 能力协商行为；界面区分配置启用与执行启用 | 默认无任务；显式启用后有结果；停用后不产生新派发；历史可继续查询 |
| 真实成功路径 | 隔离测试目标返回允许状态码和匹配正文，真实 Agent 执行并回传 | 页面可从配置定位到原始结果，结果所属节点、版本和计划时间一致 |
| 失败与缺测 | 分别注入 HTTP 错误、内容不符、TLS 错误、策略拒绝、Agent 断连、任务超时 | 服务失败与无法观测分开；不能把缺测算成功，也不能把策略拒绝归为目标宕机 |
| 统计核对 | 用固定计划槽数据核对成功、失败、缺测、覆盖率与有效区间 | 原始结果与统计一致；零分母显示不可用；未知历史与未成熟窗口有说明 |
| 生命周期 | 检查编辑版本冲突、删除、重复结果、迟到结果及重启 | 旧任务不污染新版本；重复结果不重复计数；错误可恢复且可解释 |
| 浏览器联调 | 在真实后端完成创建、编辑、查询、删除与刷新 | 明暗主题、360/768/1440 px 均通过；保留对应提交和截图 |

**发布限制：** 维护排除、服务事件和证书提醒尚未完成时，应在功能说明中明确限制。仅展示证书有效期不等于具备证书告警。基础能力若独立发布，应使用实验性或明确限定范围的说明。

### 17.3 告警与维护接入（ALT-02 / ALT-03 / SVC-03）

**用户结果：** 网站持续异常或证书即将过期时收到一次可定位的通知，维护期间保持记录且不轰炸。

实施前先确定：检查归属的策略、节点选择语义、维护窗口时区与边界、多观测点触发条件，以及维护是否排除在可用性分母之外。将决定写入模块设计文档和 API 契约。

- 服务异常使用既有事件及 Outbox 模型，避免为 HTTP 再建一套发送机制。事件应关联服务、观测点与故障类型。
- 为触发、持续、恢复分别设置明确条件；状态码改变不应无依据地创建重复活动事件。
- 证书提醒建议采用 14/7/1 天阈值，按服务、证书指纹和阈值去重；更换证书后重新计算，不能沿用旧证书的通知状态。
- 维护中保留原始观测；窗口结束时只对仍然满足规则的故障通知，不补发已恢复故障。
- 告警链接进入有权限校验的服务或事件详情，恢复对应节点与时间范围。

**验收：** 使用模拟接收端验证重启、发送超时、重复检查、证书轮换和维护边界；同时核对事件数、投递记录与实际收件数。把“已投递”“结果未知”“待重试”分开，不承诺外部渠道绝对只发送一次。

### 17.4 性能与运维证据（PERF-01 / SYS-01—03）

在增加更多探测类型之前，先记录现有版本的运行成本。测试规模按5、50节点逐步增加；依用户2026-10-19明确的自用范围，100/500节点不再列为必需验收。

每份报告至少记录硬件、系统、提交、节点数、采样和检查频率、服务数、通知故障比例、数据保留设置，以及预热和持续时间。观测 CPU、内存、数据库增长、查询 P95、任务延迟、缺测率、投递积压和清理速度。

24 小时稳定性测试应覆盖短时断网、Server 重启和外部通知不可用；恢复后确认无持续积压和不可解释的统计变化。备份演练在隔离环境恢复，并验证配置、历史与必要凭据，不能以成功生成文件替代恢复验收。

**完成条件：** 发布实际测得的承载边界和配置建议；未测规模明确标为未验证。若清理吞吐低于数据增长速度，先解决保留与查询成本，再扩大默认使用规模。

### 17.5 本轮结束时交付什么

- 一份实施台账：任务 ID、当前状态、依赖、提交、PR、验收与发布证据。
- 一套可重复的隔离测试数据和故障注入步骤。
- 每个已完成工作包的用户文档、升级说明及已知限制。
- 下一轮排期：依据未通过验收项和真实使用反馈调整，不自动继续增加监控种类。

近期取舍建议：先让已有 HTTP 能力具备真实验收证据，同时收敛 M1/M2 已有成果；随后补维护与告警闭环，再推进网络质量统计、定时备份与容量验证。远程终端、复杂主题市场和大型可观测平台能力继续暂缓。

### 17.6 范围策略运行闭环工作包（ALT-02，近期优先）

**目标：** 用户保存策略后，能够确认生效时间、命中节点和实际告警结果；升级前后的同一故障保持连续。

建议拆成以下独立可评审变更，按依赖实施。下表属于待交付规格，不是完成记录。

| 顺序 | 工作项 | 实施要求 | 验收证据 |
| --- | --- | --- | --- |
| A | 确定运行权威与启用契约 | 明确旧规则和范围策略谁负责执行；定义首次切换、再次启动、停用及异常时行为；不得同时生成两套通知 | 状态转换说明、启动失败与重启测试 |
| B | 接入评估循环 | 在事件核对与评估前完成规则同步；失败时不得把部分同步状态当成完整结果；定义配置保存至生效的延迟 | 真实 Store 与评估器测试，含同步失败注入 |
| C | 保持旧故障连续 | 迁移保持规则身份、活动事件、原阈值、恢复条件、冷却和待投递任务；重复迁移幂等 | 升级前后事件及投递快照比较，无批量重发 |
| D | 动态范围与管理变更 | 标签变更、新节点、策略禁用、覆盖与回退均重新计算；管理关闭与实际恢复使用不同原因 | 全局→标签→指定节点→回退场景及并发版本冲突测试 |
| E | 通知竞争与重启 | 定义任务已领取时策略变化的处理；旧任务不能无限继续使用过期配置；外部发送结果未知须可解释 | 模拟发送超时、进程重启、禁用与发送竞争，核对收件及投递记录 |
| F | 页面与运行状态一致 | 将当前固定的执行未启用状态替换为真实状态；区分保存、预览、已生效、执行异常；展示最近成功应用时间或等价证据 | 真实后端浏览器流程，明暗主题及三种宽度 |
| G | 恢复与配置转移 | 完整数据库恢复覆盖策略及绑定；可移植 JSON 另行版本化，不直接复制依赖原密钥的渠道密文 | 隔离恢复验证；缺失渠道、模板、节点引用和旧格式兼容测试 |

**必须先决策的边界：** 启用是否持久化；配置保存后同步执行还是下一轮生效；超出策略或绑定上限时如何保持原有监控；运行中删除节点时如何关闭关联故障。把选定行为写入模块文档，再据此编写测试，不能仅由异常处理代码隐式决定。

**完成门槛：** 至少完成一次“创建策略→新增匹配节点→制造故障→收到通知→修改标签→解释关闭或回退→重启→恢复”的完整验收。API、页面和通知表达一致后，才能把 ALT-02 从基础实现改为已完成；合并和发布状态仍单独记录。

**实施台账字段：** 任务 ID、负责人、依赖提交、实现提交、PR、代码状态、验收状态、已知限制、发布版本、证据位置。状态建议使用“未开始／实现中／待验收／待评审／已合并／已发布”，失败的验收必须保留原因，不能用一项统一完成百分比替代。

### 17.7 策略配置转移交付规格（ALT-02 子任务）

**用户故事：** 我把一套告警策略迁到另一套 MyProbe，明确选择目的地渠道、节点和模板；确认前能看到实际变更，网络超时后重试不会多建一套策略。

**第一版范围：** 只新增策略，不按名称或源 ID 覆盖目的地策略。策略包与节点配置包分别版本化；数据库备份承担完整状态恢复。策略包不携带渠道凭据、运行绑定、活动事件、发送任务和原环境数据库版本号。

用户流程为：导出策略 → 上传文件 → 选择引用映射 → 预览归一化配置及冲突 → 确认提交 → 查看创建结果及生效状态。映射页面分别展示渠道、显式节点和模板；标签规则展示目的地当前命中示例，并解释未来会动态匹配。

| 子任务 | 具体要求 | 验收结果 |
| --- | --- | --- |
| ALT-02-G1 格式与校验 | 固定 format/version，拒绝未知版本和不支持字段；区分缺省恢复窗口与显式零；明确请求大小和数量限制 | 不兼容文件有具体错误，文件中没有秘密，旧记录导出后语义不丢失 |
| ALT-02-G2 引用映射 | 所有使用到的源引用必须显式映射；目的地引用必须存在；同环境也不得偷偷按名称匹配 | 缺失映射定位到具体策略与字段；输入文件不被预览修改 |
| ALT-02-G3 预览一致性 | 返回归一化字段、目的地引用、冲突与新增数量；提交重新校验；设计预览摘要或版本凭据，使提交内容与用户确认内容一致 | 预览后策略冲突、模板删除或节点变化，不产生部分创建；需要重新确认的变化能解释 |
| ALT-02-G4 原子与幂等 | 全批策略和重试记录同事务；请求键与类型化内容摘要绑定；相同键及内容返回原始结果，异内容明确冲突 | 并发请求、响应丢失、进程重启只创建一批；后续删除策略不会被重试复活 |
| ALT-02-G5 管理 API | 统一鉴权、CSRF、禁止缓存、严格 JSON、请求体上限及脱敏错误；导入上限与单条编辑上限分别声明 | 未登录/缺少 CSRF 被拒；超限与无效数据不写库；409 冲突与输入错误可区分 |
| ALT-02-G6 页面与结果 | 上传、映射、预览、提交分步展示；内容修改后旧预览失效；不把失败重试自动换成新请求键 | 双击、刷新及超时重试不重复；显示历史创建 ID、重放标记与下一轮生效说明 |

**需在实现前定稿的契约：** 策略数组顺序、空映射与省略映射是否影响摘要；预览有效期与目的地变更检测粒度；错误响应字段；幂等记录达到保留上限后的处理。当前代码中的容量边界属于实现限制，不代表经过完整容量验证；不得静默清除历史记录而失去重试保证。

**提交时引用一致性：** 服务层预检不能代替事务内最终检查。对渠道、节点和模板逐项确认写入前的存在性与删除竞争行为，避免校验通过后写入悬空引用。已经成功提交的同内容重试应返回历史结果，不因目的地后续变化重新创建或失败；界面说明返回的是当时创建的 ID，不保证这些对象现在仍存在。

**最小验收矩阵：** 正常跨环境导入；缺少映射；重复源 ID；非法阈值；启用策略冲突；第二条失败时第一条回滚；预览后引用删除；两会话并发提交；同键改内容；服务重启后重放；成功后删除目标再重放；历史记录容量达到上限。浏览器验收使用真实后端及本地通知接收端，覆盖明暗主题和 360/768/1440 px。

**发布产物：** 格式示例、映射操作说明、API 契约、升级与备份影响、自动化测试结果、真实浏览器证据及已知限制。只有整个流程验收后才把“策略导入”标为可用，不能仅凭 Store 或服务层函数通过测试宣布交付。

### 18.1 用户价值与成熟项目对标

用户最需要的是发现问题、理解问题、处理问题后知道是否恢复。首页美化和更多图表可以继续优化，但不应挤占告警可信度、服务监控及恢复能力的投入。

| 对标对象 | 官方资料可确认的方向 | MyProbe 应吸收的设计 | 本轮取舍 |

| 哪吒监控 | Dashboard/Agent 管理与服务监控 | 从节点状态进入服务检查、通知和管理的完整路径 | 保留主动出站架构；不引入远程终端与任意任务执行 |

### 18.2 开工前的基线收敛

建立一份实施台账，每项填写：任务 ID、负责人、用户结果、依赖、分支、提交、PR、检查证据、发布版本、已知限制。状态统一为“待设计 / 实现中 / 待验收 / 待评审 / 已合并 / 已发布”；不能只用“完成”笼统描述。

1. 对未提交代码先记录归属和差异，再选择继续原任务或隔离新任务。不得覆盖未完成工作。
2. 从远端最新主线核对已合并能力，检查叠加分支依赖；未经负责人明确授权不合并。
3. 复核每个待集成分支的迁移编号、共享类型、API 路径和前端资源，避免分别可用、合并后冲突。
4. 在隔离环境复现当前构建；已有失败记录复现条件和所属修复，不能把失败基线作为新功能验收通过。
5. 原有章节的时间估算属于完整路线初始估算，不代表今天剩余工作量。以下工作包设计完成后重新估算。

### 18.3 第一交付批次：维护窗口完整流程

**关联任务：ALT-03；依赖：事件/投递与范围策略。** 使用流程：选择节点或标签 → 填写起止时间与原因 → 预览冻结成员 → 创建 → 查看抑制状态 → 到期或取消。

| 工作包 | 实施内容 | 可核验的完成条件 |
| --- | --- | --- |
| MAINT-01 列表契约 | 完成鉴权、禁止缓存、参数限制、空数组及分页；ID 游标与时间排序分开说明 | 无权限不可读；翻页不重复、不漏静态数据；取消及已删除节点的历史仍可解释 |
| MAINT-02 范围预览 | 显式节点与标签 all/any；返回精确成员、选择来源、时区及通知影响 | 空命中拒绝；预览后节点删除或标签命中变化，提交要求重新预览；不静默扩大范围 |
| MAINT-03 创建一致性 | 服务端确定操作者；写入前校验确认内容；事务保存窗口、成员及必要审计 | 同内容重试不重复建窗口；同请求键异内容冲突；任一成员无效不部分落库 |
| MAINT-04 取消 | 提交窗口版本、记录取消时间与操作者；保留历史 | 并发旧版本冲突；重复请求结果可解释；取消一个窗口不解除另一个窗口的抑制 |
| MAINT-05 管理页面 | 先做列表及详情，显示即将开始、进行中、已结束、已取消；日历视图可后置 | 本地时间与时区明确；可展开冻结成员；创建结果不确定时保留重试身份 |
| MAINT-06 事件解释 | 事件与投递详情展示维护原因、关联窗口和抑制结果 | 用户能区分“故障仍在”“通知被抑制”“外部发送结果未知” |
| MAINT-07 发布验收 | 真实 Store、评估器、工作线程、API、浏览器和本地接收端联调 | 下列矩阵全部通过；备份恢复后保留历史及行为；文档与发布限制一致 |

MAINT-03 的幂等机制是待实施要求，不因策略导入已有幂等机制就假设维护自动具备。预览摘要也不能代替权限校验与事务内引用校验。涉及新表或字段时使用新的前向迁移。

必须覆盖：开始前、开始瞬间、结束瞬间；跨时区输入；重叠窗口；取消前未开始/正在进行；删除成员；故障完全发生并恢复于维护内；维护前已通知而维护内恢复；维护结束仍异常；结束时数据陈旧；进程停机跨越整个窗口；待发送和已领取任务；网络发送已经开始；恢复备份后再启动。

验收以“事件记录、逻辑投递、实际接收”三者对照：维护内完整恢复的故障零补发；持续异常在获得新鲜观测后发送一次当前摘要；未知观测不伪造恢复。外部发送已开始时不能保证撤回，界面和文档必须准确说明。

### 18.4 第二交付批次：知悉、静默与通知降噪

**关联任务：ALT-03、ALT-05。** 知悉回答“有人处理吗”，静默回答“暂时是否继续通知”，恢复回答“故障是否消失”。三者独立。

| 工作包 | 行为要求 | 验收重点 |
| --- | --- | --- |
| ACK-01 事件知悉 | 记录操作者、时间、备注；知悉默认不静默 | 双击与重试不重复动作；活动故障保持 firing；备注不进入公开 API |
| SIL-01 限时静默 | 明确事件级范围与截止时间，支持取消；提供“知悉并静默”组合操作 | 静默内继续观测；恢复即结束事件；到期遇陈旧数据不强行通知 |
| SIL-02 抑制组合 | 定义维护和静默并存的优先顺序与解释 | 任一有效抑制仍在时不发；解除最后一个抑制后按新鲜状态处理 |
| AGG-01 通知聚合 | 先按策略、渠道、通知类型在有限时间窗聚合，设置消息长度与节点数上限 | 不合并无权限内容；重启不丢聚合任务；恢复后的旧故障消息不误导 |

聚合必须保留逐事件的投递关联和重试记录。消息摘要只是展示方式，不能把多个故障合成一个无法定位的事件。先测量告警风暴下的队列与接收体验，再决定默认聚合窗口。

### 18.5 第三交付批次：服务可用性闭环

复用 HTTP 分支已有协议、执行器、管理与统计，先核验真实 Agent 流程，再增加下列能力：

1. **服务事件：** 为每个服务和观测点保留可解释状态；使用现有事件与 Outbox，不单独实现另一套通知可靠性。
2. **证书提醒：** 显示有效期和提醒投递是两项能力；按服务、证书身份和提醒档位去重，测试换证、相同证书重报、临界时刻与重启。
3. **维护统计：** 保存原始观测，统计返回维护排除量；重叠窗口取并集，不能重复扣减。告警抑制上线不代表成功率分母已支持维护排除。
4. **诊断体验：** 把 DNS、TCP、TLS、状态码、内容断言、任务未执行和能力不支持分开呈现；通知深链恢复服务、观测点和时间范围。

发布门槛：主机在线但网站失败能触发服务事件；Agent 离线显示未知而非网站正常；旧 Agent 不因能力缺失制造服务故障；换证后提醒正确；默认不泄漏 URL 秘密、正文和内部目标地址。

### 18.6 第四交付批次：网络与系统运维

网络先完成计划槽、执行状态与统计契约，再开发多节点图表。优先交付覆盖率、失败分类和样本数；P95 与抖动必须通过人工数据对照及跨桶合并验证。旧数据不具备所需分布时明确不支持，不能用平均值冒充。

运维按“看见系统问题 → 导出诊断 → 定时备份 → 恢复演练 → 容量声明”的顺序推进。健康页应能识别采集正常但通知积压、数据库增长失控及清理停滞。诊断包默认脱敏，导出前展示内容范围，不包含令牌、完整数据库或备份解密密钥。

容量测试以5、50节点递进；100/500节点仅为可选扩展，不计入本次交付门槛。记录峰值常驻内存、CPU、磁盘增长、请求 P95、队列等待与缺测率；不能把一次函数基准测试的累计分配量当成进程峰值内存。24 小时稳定性结果附硬件、频率、提交和故障注入条件。
